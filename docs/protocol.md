# WooCast Protocol v1 (WCP/1)

Протокол передачи экрана/окна ПК на приёмник (Android TV) внутри локальной сети.
Спроектирован под низкую задержку и минимальный код на принимающей стороне:
три независимых канала — обнаружение (UDP), управление (TCP, JSON Lines), медиа (TCP, бинарный фрейминг).

| Параметр | Значение |
|---|---|
| Версия | `1` (поле `wc` в JSON, `version` в бинарном заголовке) |
| Транспорт | IPv4 LAN, UDP + TCP |
| Кодирование управления | UTF-8 JSON Lines (`\n`), максимум 64 КиБ на строку |
| Кодирование видео | H.264 Annex-B (Baseline/Main/High, без B-кадров) |
| Порт обнаружения | `47810/udp` |
| Порт управления | `47811/tcp` |
| Порт медиа | `47812/tcp` (может быть заменён полем `mediaPort` в `stream_ready`) |

Зарезервированные диапазоны: `47810–47819`. Порты настраиваются на приёмнике; фактические значения
всегда сообщаются отправителю в ответе `announce` / `hello_ack`, поэтому менять их на стороне
отправителя вручную не требуется.

---

## 1. Обнаружение (UDP, порт 47810)

### 1.1 Пассивное обнаружение (основной путь)

Приёмник каждые **3 секунды** рассылает широковещательный пакет `announce`:

* адрес `255.255.255.255:47810` и направленный broadcast каждого интерфейса;
* дополнительно multicast `239.255.77.87:47810` (для сетей, где broadcast ограничен).

Отправитель слушает `47810/udp` и наполняет список устройств по этим пакетам.
Устройство считается **офлайн**, если `announce` не приходил **10 секунд**.

```json
{
  "wc": 1,
  "t": "announce",
  "id": "6f1c8a2e4b7d4f10",
  "name": "WooCast TV — гостиная",
  "model": "Xiaomi Mi Box S",
  "version": "1.0.0",
  "proto": 1,
  "controlPort": 47811,
  "mediaPort": 47812,
  "state": "idle",
  "caps": {
    "codecs": ["h264"],
    "maxWidth": 1920,
    "maxHeight": 1080,
    "maxFps": 60,
    "audio": ["aac", "opus"],
    "lowLatencyDecode": true
  }
}
```

`state`: `idle` | `busy` (кто-то уже транслирует).

### 1.2 Активное сканирование (кнопка «Обновить» / ручной IP)

Отправитель посылает `discover` на broadcast-адреса и (при ручном вводе) на конкретный IP:

```json
{ "wc": 1, "t": "discover", "id": "2a77b0c1d3e94f55", "name": "DESKTOP-7", "proto": 1 }
```

Приёмник обязан ответить **unicast**-пакетом `announce` на адрес и порт источника запроса.
Ответ на `discover` не должен рассылаться в broadcast (иначе лавина ответов).

### 1.3 Ручное подключение по IP

Ручной ввод `host` или `host:port` не требует обнаружения: отправитель сразу переходит к
управляющему соединению, используя порт по умолчанию `47811`, если порт не указан.

## 2. Управляющий канал (TCP, порт 47811)

Одно TCP-соединение на сессию. Каждое сообщение — одна строка JSON, завершённая `\n`.

Общие поля: `wc` (всегда `1`), `t` (тип), `id` (опциональный идентификатор запроса),
`re` (идентификатор запроса, на который отвечают). Ответ на запрос обязан содержать `re`.

### 2.1 Последовательность установления сессии

```
Отправитель                                   Приёмник
    |                                             |
    |--- hello -------------------------------->  |
    |  {id, name, app:{name,version}, proto}       |
    |                                             |
    |  <------------------------------- hello_ack |
    |    {re, session, token, receiver, proto}     |
    |                                             |
    |--- stream_request ----------------------->  |
    |  {re2, video:{...}, source:{...}, audio:{}}  |
    |                                             |
    |  <------------------------ stream_ready --- |  (или stream_reject)
    |    {re:re2, mediaPort, token}                |
    |                                             |
    |=== TCP connect -> mediaPort ==============>  |
    |=== media handshake + поток кадров ========>  |
    |                                             |
    |--- stream_start ------------------------->  |  (после медиа-хендшейка)
    |  <----------------------------- started --- |
    |                                             |
    |--- stats (1 Гц) ------------------------->  |  (телеметрия для OSD)
    |--- ping (по таймауту простоя) ----------->  |
    |  <-------------------------------- pong --- |
    |                                             |
    |--- stop --------------------------------->  |
    |  <---------------------------- stopped --- |
```

### 2.2 Сообщения отправитель → приёмник

| `t` | Поля | Описание |
|---|---|---|
| `hello` | `id`, `name`, `app{name,version}`, `proto` | Начало сессии. `id` — стабильный идентификатор ПК. |
| `stream_request` | `re`, `video{codec,width,height,fps,bitrate,profile}`, `source{type,id,title}`, `audio{enabled,codec,bitrate}` | Запрос на старт трансляции. `source.type`: `display` \| `window`. |
| `stream_start` | — | Медиа-соединение установлено и заголовок отправлен; можно показывать видео. |
| `stats` | `fps`, `kbps`, `dropped`, `queueMs`, `rttMs` | Телеметрия 1 раз в секунду, только для OSD. Приёмник игнорирует неизвестные поля. |
| `ping` | `ts` | Проверка живости, если по каналу нет трафика. |
| `stop` | — | Завершение трансляции по инициативе ПК. |
| `bye` | — | Завершение сессии, соединение закрывается. |

Пример `stream_request`:

```json
{
  "wc": 1, "t": "stream_request", "re": "3",
  "video": { "codec": "h264", "width": 1920, "height": 1080, "fps": 60, "bitrate": 8000, "profile": "high" },
  "source": { "type": "display", "id": "0", "title": "Весь экран" },
  "audio": { "enabled": false, "codec": "aac", "bitrate": 128 }
}
```

### 2.3 Сообщения приёмник → отправитель

| `t` | Поля | Описание |
|---|---|---|
| `hello_ack` | `re`, `session`, `token`, `receiver{id,name,version}`, `proto` | Принято. `token` нужен для медиа-хендшейка, `session` — идентификатор сессии. |
| `stream_ready` | `re`, `mediaPort`, `token` | Приёмник готов принимать медиа на указанном порту. |
| `stream_reject` | `re`, `reason`, `message?` | Отказ. `reason`: `busy` \| `unsupported_codec` \| `unsupported_resolution` \| `declined` \| `internal`. |
| `started` | `re` | Приёмник начал декодирование (первый кадр отрисован). |
| `request_keyframe` | — | Приёмник потерял кадры и просит ключевой кадр (отправитель форсирует IDR). |
| `stats` | `fps`, `dropped`, `late`, `latencyMs` | Телеметрия приёмника, 1 Гц. |
| `pong` | `re`, `ts` | Ответ на `ping`. |
| `stopped` | `re` | Трансляция остановлена. |
| `error` | `re`, `code`, `message` | Ошибка протокола. `code`: `protocol_error` \| `bad_token` \| `bad_state` \| `internal`. |
| `input` | `input{seq,buttons,lx,ly,rx,ry,lt,rt,device?}` | Состояние управления с геймпада, подключённого к приёмнику. До 60 раз в секунду и только при изменениях; раз в полсекунды — даже без изменений, чтобы компьютер видел, что связь жива. |

#### Управление с контроллера (`input`)

Контроллер подключается к приставке или телефону, а игра работает на компьютере,
поэтому состояние уходит **от приёмника к отправителю** — в обратную сторону от видео.
На компьютере оно подаётся в виртуальный геймпад (драйвер ViGEmBus), и игра видит
обычный геймпад с аналоговыми осями и курками.

| Поле | Смысл |
|---|---|
| `seq` | Порядковый номер: растёт на единицу. Позволяет заметить пропуск. |
| `buttons` | Битовая маска нажатых кнопок (см. ниже). |
| `lx`, `ly` | Левый стик, от −32768 до 32767, ноль в покое. |
| `rx`, `ry` | Правый стик, те же пределы. |
| `lt`, `rt` | Курки, от 0 до 255. |
| `device` | Название контроллера — показывается на компьютере. |

Маска кнопок: `A`=1, `B`=2, `X`=4, `Y`=8, `LB`=16, `RB`=32, `Back`=64, `Start`=128,
`L3`=256, `R3`=512, `Guide`=1024, `вверх`=2048, `вниз`=4096, `влево`=8192, `вправо`=16384.

Названия кнопок нейтральные намеренно: Android приводит любой контроллер к общему виду
(крест DualShock приходит как `A`, круг — как `B`), поэтому отдельной поддержки
конкретных моделей не требуется.

**Ось Y направлена вверх положительно** — как у геймпада Xbox и в отличие от Android,
где «вверх» отрицательно. Разворот делается на приёмнике, чтобы обе стороны говорили
об одном и том же.

### 2.4 Правила состояний

* До `hello_ack` приёмник принимает только `hello`; остальные сообщения → `error{code:"bad_state"}`.
* Повторный `stream_request` во время активной трансляции → `stream_reject{reason:"busy"}`.
* Если медиа-соединение не установлено в течение **5 секунд** после `stream_ready`, приёмник
  освобождает сессию и возвращается в `idle`.
* Разрыв управляющего TCP-соединения немедленно останавливает трансляцию и закрывает медиа-соединение.
* Обе стороны обязаны игнорировать неизвестные поля JSON и неизвестные типы сообщений
  (совместимость вперёд).

## 3. Медиа-канал (TCP, `mediaPort`)

### 3.1 Хендшейк

Сразу после установки TCP-соединения отправитель передаёт **20 байт** заголовка (big-endian):

| Смещение | Размер | Поле | Значение |
|---|---|---|---|
| 0 | 4 | `magic` | ASCII `WCM1` (`57 43 4D 31`) |
| 4 | 1 | `version` | `1` |
| 5 | 1 | `codec` | `1` = H.264 Annex-B |
| 6 | 2 | `flags` | бит 0 — присутствует аудио (зарезервировано, v1 = 0) |
| 8 | 8 | `token` | токен из `hello_ack` |
| 16 | 4 | `reserved` | `0` |

Приёмник проверяет `magic`, `version` и `token`. При несовпадении — закрывает соединение
(при неверном токене дополнительно отправляет `error{code:"bad_token"}` по управляющему каналу).

### 3.2 Кадрирование пакетов

Далее — непрерывный поток пакетов, по одному пакету на **access unit** H.264:

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 4 | `payloadLength` — длина полезной нагрузки, big-endian, максимум 4 МиБ |
| 4 | 8 | `ptsMicros` — метка времени кадра, микросекунды, монотонно возрастает |
| 12 | 1 | `flags`: бит 0 — ключевой кадр (IDR), бит 1 — конфигурация (SPS/PPS), бит 2 — аудио |
| 13 | 1 | `reserved` = 0 |
| 14 | 2 | `reserved` = 0 |
| 16 | N | `payload` |

Заголовок пакета — **16 байт**. Порядок пакетов строго соответствует порядку отображения.

### 3.3 Требования к полезной нагрузке

* Каждый access unit начинается с AUD NAL (`00 00 00 01 09 ...`). Отправитель обязан включать AUD
  (в ffmpeg: bitstream-фильтр `h264_metadata=aud=insert`), это позволяет приёмнику делить поток
  без разбора slice-заголовков.
* Поток не содержит B-кадров; каждый кадр может ссылаться только на предыдущие.
* SPS/PPS передаются в начале потока и **повторяются перед каждым IDR** (in-band, без AVCC-заголовков).
  Приёмник обязан обновлять `csd-0`/`csd-1` при изменении SPS/PPS.
* Интервал ключевых кадров (`IDR`) по умолчанию — **2 секунды** (или по требованию приёмника).
* Приёмник **обязан** быть устойчив к потере кадров: при отставании отображать только актуальный кадр
  (drop late frames), не накапливая очередь.

### 3.4 Обратное давление и переполнение

Отправитель не буферизует неограниченно: очередь кадров ограничена (**≤ 4 кадра**), при
переполнении запись блокируется, что через pipe останавливает чтение вывода энкодера и
заставляет кодировщик пропускать кадры захвата. Это сохраняет низкую задержку за счёт частоты кадров —
предпочтительное поведение для зеркалирования экрана.

### 3.5 Смена параметров на ходу

Отправитель вправе изменить параметры потока, не разрывая сессию: заново запустить кодировщик
с другим битрейтом или частотой кадров и продолжить передачу в то же медиа-соединение.
Новые SPS/PPS приходят в потоке (см. п. 3.3), поэтому отдельного сообщения протокола не требуется.

Основание для таких изменений — сообщения `stats` от приёмника: если его частота декодирования
устойчиво ниже отправляемой, отправитель снижает частоту кадров; если растёт очередь отправки —
снижает битрейт. Приёмник обязан корректно пережить смену SPS/PPS: при изменении разрешения —
пересоздать кодек, при изменении только частоты кадров — продолжить декодирование.

### 3.6 Аудио

Пакеты с битом 2 в `flags` несут аудио: **AAC-LC в ADTS**, по одному кадру на пакет.
Поле `ptsMicros` лежит на **той же шкале**, что и видео.

* Отправитель захватывает системный звук (WASAPI loopback), кодирует его в AAC-LC
  (по умолчанию 160 кбит/с, 48 кГц, стерео) и передаёт кадры целиком, вместе с
  семибайтовым заголовком ADTS.
* Метки времени звука считаются по счётчику сэмплов: один кадр AAC — это всегда
  1024 сэмпла, поэтому шкала получается ровной. Начало шкалы привязано к тем же
  монотонным часам, что и у видео.
* Приёмник вырезает заголовок ADTS (полезная нагрузка идёт в `MediaCodec` без него),
  а из заголовка строит `csd-0` — двухбайтовый `AudioSpecificConfig`:
  5 бит типа объекта, 4 бита индекса частоты, 4 бита каналов и 3 нулевых бита.
* Наличие звука объявляется заранее: бит 0 в `flags` медиа-заголовка (см. п. 3.1)
  и поля `audio.enabled` / `audio.codec` в `stream_request`.

#### Синхронизация звука и изображения

Абсолютные значения `ptsMicros` у звука и видео **не совпадают**: кодировщики дают
разную задержку (захват экрана и NVENC выдают первый кадр заметно позже, чем AAC).
Разница постоянна в пределах сессии — измерено около 0,5 с на старте и нулевой дрейф
дальше (темп звука совпадает с эталонным 21,33 мс/кадр).

Поэтому приёмник **ведёт счёт по звуку**: AudioTrack отдаёт позицию воспроизведения,
которая вместе с меткой первого аудиокадра образует текущее время потока. Видеокадр
выводится не сразу после декодирования, а когда время потока достигнет его `ptsMicros`
(в Android для этого есть `releaseOutputBuffer(index, renderTimestampNs)`).

Если звук отключён или недоступен, приёмник ведёт счёт по своим часам и выводит видео
немедленно — как в v1.

## 4. Рекомендации по реализации

**Отправитель (ПК).**
Захват: `ddagrab` (Desktop Duplication, GPU) с откатом на `gdigrab` для полного экрана и на
`gdigrab -i title=<окно>` для окна. Кодирование: аппаратный энкодер по наличию
(`h264_nvenc` → `h264_qsv` → `h264_amf` → `libx264`), обязательны `zerolatency`, `bf=0`, `g=<2*fps>`.
Читать stdout энкодера отдельной задачей, резать поток по AUD, писать в сокет из ограниченной очереди.

**Приёмник (Android TV).**
Один поток — UDP-discovery, один — TCP-акцептор управления, один — TCP-акцептор медиа, один — разбор
и подача кадров в `MediaCodec`, рендер в `Surface` через `SurfaceView`. Включать
`KEY_LOW_LATENCY` на API 30+, `KEY_PRIORITY=0`, сбрасывать кодек при смене SPS/PPS,
при отставании — `releaseOutputBuffer(index, false)` для просроченных кадров.
`MediaCodec` работает в режиме `Surface` (не ByteBuffer), чтобы декодирование шло в GPU.

## 5. Что осознанно НЕ входит в v1

* Шифрование и аутентификация (доверенная локальная сеть). В v1.2 планируется опциональный
  pre-shared key: HMAC-SHA256 на `hello` + AES-GCM на медиа-пакеты.
* UDP/RTP с FEC и NACK — TCP достаточен для проводной LAN; для «шумного» Wi-Fi планируется v2.
* Передача управления (мышь/клавиатура с ТВ на ПК) — запланирована как `event`-сообщения в v1.3.
* IPv6, mDNS, проброс через NAT.
