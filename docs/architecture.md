# Архитектура WooCast

## 1. Общая картина

Три независимых компонента, связанных одним контрактом — протоколом
[WCP/1](protocol.md).

```
WooCast/
├── src/
│   ├── WooCast.Protocol/   net9.0, без UI и платформенных зависимостей
│   │                       → модели сообщений, JSON Lines, UDP-discovery, TCP-сервер/клиент, фрейминг
│   ├── WooCast.Desktop/    Avalonia 11, MVVM (CommunityToolkit.Mvvm)
│   │                       → экран устройств, настройки стрима, статус, встроенный лог
│   └── WooCast.Cli/        net9.0 console
│                           → «голый» отправитель: удобно тестировать приёмник и протокол
├── android/
│   └── app/                Kotlin, Compose for TV, MediaCodec, minSdk 24
└── tools/                  PowerShell: подготовка окружения (ffmpeg, dev-env)
```

Разделение ответственности:

* **WooCast.Protocol** ничего не знает про UI и про то, как получается видео. Он умеет:
  обнаруживать приёмники, вести управляющую сессию, резать Annex-B на access unit'ы и
  передавать пакеты по TCP.
* **WooCast.Desktop** отвечает за представление: список устройств, настройки, телеметрия.
  Захват и кодирование вынесены в `Capture/` и работают как отдельная подсистема.
* **Приёмник** — независимая реализация протокола на Kotlin. Общего кода с C# нет намеренно:
  приёмник должен собираться стандартным Android-тулчейном без кроссплатформенных прослоек.

## 2. Стек и почему так

| Решение | Выбор | Альтернативы и причина отказа |
|---|---|---|
| UI ПК | **Avalonia UI 11** | Electron: +150 МБ рантайма и слой JS на пути видеопотока. WPF: только Windows, не даёт задел на Linux. |
| Захват (этап 1) | **ffmpeg `ddagrab`** → `gdigrab` | Свой захват: дольше до рабочего результата. `ddagrab` использует Desktop Duplication API и отдаёт кадры на GPU. |
| Захват (этап 2) | **Windows.Graphics.Capture + Media Foundation** (Vortice.Windows) | Позволяет захватывать конкретное окно, включая перекрытые, и убирает внешний процесс. |
| Кодирование | **h264_nvenc / h264_qsv / h264_amf → libx264** | Автодетект по факту запуска, а не по модели GPU. |
| Транспорт | **TCP** | UDP/RTP с FEC даёт выигрыш на «шумном» Wi-Fi, но заметно сложнее. Для проводной LAN TCP достаточно: см. п. 4. |
| Приёмник | **Kotlin + Compose for TV + MediaCodec** | ExoPlayer даёт готовый разбор контейнера, но и лишнюю буферизацию (секунды вместо десятков миллисекунд). |

## 3. Компоненты отправителя

```
WooCast.Desktop
├── Views/            MainWindow, DeviceCard, SettingsPanel — только вёрстка
├── ViewModels/       MainViewModel (список устройств, состояние), SettingsViewModel
├── Services/
│   ├── DeviceDiscoveryService   UDP 47810: слушает announce, шлёт discover, ведёт TTL устройств
│   ├── StreamSession            управляющий TCP + медиа TCP, состояние сессии
│   └── EncoderProbe            один раз при старте: какие энкодеры и ddagrab доступны
└── Capture/
    ├── FfmpegCaptureSource      аргументы ffmpeg, запуск процесса, чтение stdout
    ├── AnnexBSplitter           поток байт → access unit'ы (границы по AUD NAL)
    └── FramePump                ограниченная очередь → сокет, backpressure, статистика
```

Потоки и задачи:

| Задача | Роль |
|---|---|
| UI thread | Avalonia, обновление списка и телеметрии через `Dispatcher` |
| Discovery loop | `UdpClient` с `ReuseAddress`, приём announce, отправка discover по таймеру |
| Control loop | Чтение JSON Lines, корреляция ответов по `re`, keep-alive `ping` |
| stderr reader | Диагностика ffmpeg → в лог приложения (не блокирует) |
| stdout reader | Читает поток энкодера, режет на AU, кладёт в `Channel<AccessUnit>` (capacity 4) |
| Socket writer | Забирает из канала, пишет заголовок пакета и payload в TCP |

Связь «stdout → канал → сокет» принципиальна для задержки: если сеть не успевает, канал
заполняется, читатель перестаёт вычитывать stdout, pipe забивается, ffmpeg пропускает кадры
захвата. Задержка остаётся постоянной, падает только частота кадров — правильный компромисс
для зеркалирования экрана.

## 4. Бюджет задержки (цель ≤ 80 мс на проводной LAN, 1080p60)

| Этап | Ожидаемо |
|---|---|
| Захват `ddagrab` | 3–8 мс |
| Кодирование NVENC/QSV (`zerolatency`, без B-кадров) | 5–15 мс |
| Передача по TCP 1 Гбит/с при 8 Мбит/с | 1–3 мс + буферизация Nagle (отключён: `NoDelay`) |
| Декодирование MediaCodec | 10–30 мс |
| Вывод на экран ТВ (в т.ч. post-processing панели) | 20–40 мс |

Отдельно: интервал ключевых кадров 2 с даёт восстановление после сбоя за ≤ 2 с при цене ~5–8 %
битрейта. Полностью избавиться от накопления задержки на TCP помогает только переход на
RTP/UDP (v2 в [roadmap](roadmap.md)).

## 5. Компоненты приёмника

```
WooCast TV
├── ui/         Compose for TV: экран ожидания (имя + IP + подсказка), плеер, оверлей статистики
├── net/        DiscoveryResponder (UDP), ControlServer (TCP), MediaServer (TCP)
├── media/      AnnexBParser → H264AccessUnit → MediaCodecDecoder → Surface
└── service/    ForegroundService, чтобы трансляция не рвалась при уходе в фон
```

Ключевые решения приёмника:

* `MediaCodec` работает в режиме **Surface**, а не ByteBuffer — декодирование идёт на GPU,
  копирования кадров в память приложения нет.
* `KEY_LOW_LATENCY` (API 30+) и `KEY_PRIORITY = 0` — минимальная буферизация внутри кодека.
* При отставании просроченные кадры не выводятся (`releaseOutputBuffer(index, false)`),
  очередь не растёт.
* Смена SPS/PPS (например, пользователь сменил разрешение на ПК) пересоздаёт кодек на лету.
* `minSdk 24`: основная масса ТВ-приставок на Android 7+, при этом `KEY_LOW_LATENCY`
  включается условно на новых прошивках.

## 6. Захват отдельного окна

Захват отдельного окна делается **системным способом** — `Windows.Graphics.Capture`:
система отдаёт содержимое окна напрямую, поэтому перекрытие, уход окна в фон и перемещение
картинку не портят. Кадры приходят текстурами Direct3D, копируются в память и уходят
в ffmpeg потоком `rawvideo` (`-f rawvideo -pix_fmt bgra -i -`), после чего кодируются
теми же настройками, что и раньше.

Прежний способ — **обрезка снимка рабочего стола** (`ddagrab` → `hwdownload` →
`crop=Ш:В:X:Y` → масштаб) — остался запасным. Он включается сам, если системный захват
недоступен, окно его не поддерживает или первый кадр не пришёл; отключить его принудительно
можно переменной окружения `WOOCAST_NO_WINDOW_CAPTURE=1`. У запасного способа есть
честное ограничение: **перекрытые части окна покажут то, что находится сверху**.

Особенности системного захвата, выясненные на практике:

* кадр приходит **только при изменении содержимого окна** — неподвижное окно не гоняет
  кадры зря, но и частота оказывается ниже запрошенной (подстройка это учитывает);
* **свёрнутое окно система не отрисовывает**: кадры прекращаются до разворота,
  о чём приложение сообщает в журнале;
* **изменение размера окна требует пересборки потока**: кодировщику размер сообщён
  при запуске, поэтому источник пересоздаётся целиком (медиа-соединение сохраняется).

Что уже сделано:

* **Перечисление окон** (`Windows.Enumerate`): отсеиваются невидимые, свёрнутые, служебные
  окна и скрытые окна UWP (`DWMWA_CLOAKED`); границы берутся через `DWMWA_EXTENDED_FRAME_BOUNDS`,
  чтобы тень не попадала в кадр.
* **Привязка к монитору**: окно сопоставляется с монитором по своему центру, координаты
  обрезки пересчитываются в систему координат этого монитора — `ddagrab` захватывает один вывод.
* **Автослежение** (`CapturePipeline.FollowWindowLoopAsync`): раз в 700 мс проверяются границы
  окна. Изменение должно устояться две проверки подряд — иначе перетаскивание превратилось бы
  в череду перезапусков. При закрытии или сворачивании окна трансляция завершается с понятной
  причиной. Разрешение потока при этом не меняется: масштаб с полями приводит кадр к заданному
  размеру, поэтому приёмнику не нужно пересоздавать декодер.

## 7. Адаптивная подстройка

Приёмник раз в секунду присылает `stats` со своей частотой декодирования, потерями
и измеренной задержкой. Отправитель использует это, чтобы различить два принципиально
разных узких места:

| Признак | Что происходит | Реакция |
|---|---|---|
| Очередь отправки ≥ 2 кадров | Не успевает сеть | Битрейт снижается на 30 %, но не ниже 1.5 Мбит/с |
| Частота приёмника < 85 % нашей, очередь пуста | Не успевает декодер приставки | Частота кадров ступенями: 60 → 30 → 15 |

Решение принимается после трёх плохих замеров подряд и не чаще, чем раз в 5 секунд.
Смена параметров требует перезапуска кодировщика (ffmpeg не позволяет менять их на лету),
но медиа-соединение при этом не рвётся: приёмник получает новые SPS/PPS в потоке и,
если разрешение не менялось, продолжает декодировать без пересоздания кодека.

Обратный подъём параметров, когда приставка снова начала успевать, пока не реализован —
это следующий шаг: он требует гистерезиса, чтобы не раскачивать систему.

## 8. Звук

Системный звук захватывается **в процессе приложения** через WASAPI loopback
(NAudio, MIT): ffmpeg такого режима не умеет, а DirectShow-источник требует
включённого «Стерео микшера», которого на большинстве машин нет. Loopback работает
всегда, когда что-то играет, и не требует настроек системы.

Кодирование вынесено в **отдельный процесс ffmpeg**, а не в общий с видео:

```
WASAPI loopback (f32le 48 кГц)  →  ffmpeg -c:a aac -f adts  →  кадры ADTS  →  медиа-канал
ddagrab + NVENC                 →  ffmpeg -f h264          →  access unit'ы →  медиа-канал
```

Причина в том, что видео пишется в stdout как raw H.264, и примешать к нему звук можно
было бы только через контейнер, который пришлось бы разбирать на приёмнике. Два
независимых потока проще и не мешают друг другу; различить их на приёмнике позволяет
бит `Audio` в заголовке пакета.

Шкала времени звука считается **по счётчику сэмплов**, а не по моменту чтения из
кодировщика: кадр AAC — это всегда 1024 сэмпла, поэтому шкала выходит ровной и без
дрожания от буферизации (измерено: 21,33 мс/кадр при 48 кГц, дрейф 0).

Разница задержек двух кодировщиков даёт постоянное смещение (около 0,5 с: первый кадр
ddagrab+NVENC выходит заметно позже первого кадра AAC). Оно не мешает: приёмник ведёт
счёт по звуку и выводит видео по его метке времени — см. п. 3.6 спецификации протокола.

## 9. Совместимость и развитие

Протокол версионирован полем `wc` / `version`. Правила, заложенные с самого начала:

1. Неизвестные поля JSON игнорируются — новые возможности не ломают старые сборки.
2. Неизвестные типы сообщений игнорируются, а не считаются ошибкой.
3. Медиа-заголовок содержит `version` и `flags` — расширение (аудио, шифрование) без смены magic.

Планы по этапам — в [roadmap.md](roadmap.md).
